## 1. مخطط البنية (Architecture Flow)

```
┌──────────────────────── DSTSG Live Arbitration ────────────────────────┐
│                                                                        │
│  [اللاعب A] ──getDisplayMedia──► RTCPeerConnection ──┐                 │
│       │                                   ▲           │ فيديو P2P      │
│       │ offer/answer/ICE                   │           ▼ مباشر         │
│       │ (POST /api/arb/signal)             │    [لوحة الأدمن]          │
│       ▼                                    │     فيديو A │ فيديو B     │
│  ┌─────────────────────────────────────┐   │      (جنباً إلى جنب)      │
│  │  خادم الإشارات (Signaling فقط!)      │◄──┘           │             │
│  │  server-arbitration.js               │               │ أزرار:      │
│  │  • يرحّل العروض/الأجوبة/ICE           │◄──────────────┘ فوز A/B ·    │
│  │  • جلسات + توكنات (SQLite)           │     نزاع · إلغاء/استرداد     │
│  │  • نبض + منظّف انقطاع (15ث)          │               │             │
│  └──────────────┬───────────────────────┘               ▼             │
│                 │ ناقل SSE الحي القائم (/api/live)      │             │
│  [اللاعب B] ────┘  (arb:signal / arb:session /          │             │
│                     arb:resolved)                        │             │
│                                                          ▼             │
│              الحسم ⇒ نواة التسوية المعتمدة نفسها (arbResolve/arbCancel) │
│              ⇒ إفراج عن الإيداعات: الرابح +الجرة − 5% · أو استرداد كامل │
│                                                                        │
│  بديل P2P تعذّر ⇒ نشر WHIP إلى MediaMTX محلي ⇒ الأدمن يشاهد عبر WHEP   │
└────────────────────────────────────────────────────────────────────────┘
```

> **[v2.81] السطر الأخير من الرسم — بديلٌ مثبَّتٌ الآن تحت إشراف.**
> `MEDIAMTX_WHIP_URL` ما زالت غير موجودة في `.env.local` (احتياطي WHIP غير مفعّل
> عمداً)، **لكن المرحّل نفسه صار مُثبَّتاً ومشغَّلاً تحت pm2** ⇒ **الحالة الفعلية
> اليوم: P2P حصراً** في مسار الفيديو (وهو المسار الأساسي، لا بديلاً)، والمرحّل
> مُجهَّز للمراقبة ومجهَّز للنشر — **لا مكتمل للنشر بعد** لأن `MEDIAMTX_RTMP_URL`
> تنتظر قرار المالك (§9). التفاصيل في §5.

**قررارات معمارية (لماذا هكذا؟):**

| القرار | السبب |
|---|---|
| **WebRTC P2P** للفيديو | الفيديو لا يمر بالخادم إطلاقاً: صفر ترميز وصفر باندويث على معالج الهاتف (Cat S62: 4GB RAM) وعبر نفق Cloudflare المجاني. |
| **الإشارات عبر POST + ناقل SSE القائم** بدل WebSocket | لا مكتبة جديدة (`ws`) ولا منفذ إضافي عبر النفق؛ ناقل `/api/live` مُختبَر في الإنتاج منذ v2.43 ويعبر Cloudflare Tunnels أصلاً. إشارات WebRTC JSON صغيرة — أجزاء الثانية كافية تماماً للمصافحة. |
| **الحسم عبر نواة التسوية نفسها** (`settleSeatCore`) | لا مسار مال جديد قط (قاعدة AGENTS #12): نفس عقد المال v2.71+ — الرابح يستلم الجرة − 5%، سجل معاملات كامل (win/refund)، تذاكر الجولة، و`room.settled` يمنع الازدواج. الفارق الوحيد: التفويض بصلاحية الأدمن بدل عضوية الغرفة. |
| **توكن لكل لاعب في الجلسة** | الإشارة/النبض تطلبه حصراً؛ الحسم/الإلغاء يتطلبان صلاحية أدمن (role) — لا يستطيع لاعب حسم مباراته. |
| **«المباراة» = غرفة اللعب** | رهاناتها مودَعة في escrow عند البدء — وهي وحدة التحكيم الطبيعية على المنصة. |

## 3. نقاط النهاية (API)

| المسار | الدور | التصريح |
|---|---|---|
| `POST /api/matches/:roomId/start-stream` | فتح/جلب جلسة التحكيم للجولة الجارية + توكن البث (idempotent) | لاعب نشط في الغرفة |
| `GET /api/matches/mine` | **[v2.76]** جلستي: غرفة المستخدم الجارية + جلسة التحكيم المرتبطة (بلا توكنات) | مستخدم مسجل الدخول |
| `GET /api/matches` | قائمة الجلسات النشطة | أدمن/سوبر |
| `POST /api/matches/:roomId/resolve` | الحسم: `{status:'completed', winner_id}` أو `{status:'disputed'}` | **أدمن/سوبر حصراً** |
| `POST /api/matches/:roomId/cancel` | إلغاء + استرداد كامل للرهانات | **أدمن/سوبر حصراً** |
| `POST /api/arb/signal` | ترحيل `offer/answer/ice/rewatch/bye` (توكن اللاعب إلزامي) | أطراف الجلسة + الأدمن |
| `POST /api/arb/heartbeat` | نبض البث (state: idle/connecting/live/relay/failed) | لاعب بتوكنه |
| `GET /api/matches/:roomId/stream-status` | **[v2.81]** حالة بث المرحّل لطرفي المباراة (أ + ب) من MediaMTX API محلياً — `available · player_a_status{online,ready,bytes_rx,stream_duration,path,offline_since,alert} · player_b_status · arbitration_ready` + تنبيه الانقطاع > 30ث (صف `arb_stream_events` + حدث SSE `arb:stream`) | **أدمن/سوبر حصراً** |

أحداث SSE على `/api/live`: `arb:signal` (الإشارات) · `arb:session` (تحديث حالة الجلسة/انقطاع) · `arb:resolved` (حسم نهائي) · `arb:stream` **[v2.81]** (انقطاع/عودة بث المرحّل بعد تجاوز مهلة المراقبة).

## 4. التشغيل خطوة بخطوة (سيناريو كامل)

> **[v2.76]** السيناريو نفسه يعمل من **صفحة التحكيم المخصّصة** (‪#arb‬ — عنصر تنقل «التحكيم المباشر»): اللاعب من بطاقة «جلستي الحالية» فيها، والأدمن من مركز التحكيم داخلها (إحصاءات + جلسات + مشاهدة مزدوجة + حسم). مودال الغرفة وتبويب لوحة الإدارة يبقيان يعملان كما هما.

1. **لاعبان** يبدآن جولة وجه لوجه (غرفة بأي لعبة، برهان) — الرهانات تُقتطع في escrow عند البدء كالمعتاد.
2. أحد اللاعبين يفتح **مودال الغرفة** ⇒ يظهر صندوق «📺 بث التحكيم المباشر» ⇒ ينقر **مشاركة الشاشة / بدء البث** ⇒ يسمح للمتصفح بمشاركة الشاشة.
   - المؤشر: 🟡 يتم الاتصال… ⇒ 🟢 **مباشر — الأدمن يشاهد** (أو 🟠 عبر المرحّل عند سقوط P2P).
   - يمكن للاعبه الآخر مشاركة شاشته كذلك — الأدمن يشاهد الاثنين معاً.
3. **الأدمن** (أو السوبر) يفتح لوحة التحكم ⇒ تبويب **📺 التحكيم** ⇒ تظهر بطاقة الجلسة (اللاعبان + حالة بث كل منهما) ⇒ ينقرها ⇒ **المشاهدة المزدوجة**.
   - انقطاع بث أي لاععب > 15ث ⇒ ⚠️ تنبيه آلي في اللوحة (منظّف خادمي كل 5ث).
4. عند حسم النتيجة: **✅ تأكيد فوز اللاعب الأول/الثاني** ⇒ إفراج خادمي فوري عن الإيداعات (الرابح +الجرة − 5%، مع دفعة محفظة فورية للطرفين).
   - **⚖️ نزاع** أو **❌ إلغاء/إرجاع الأموال** ⇒ استرداد كامل للجميع (صفوف refund في السجل).
5. الجلسة تُقفل (لا إشارات ولا حسم مزدوج) وتُحفظ في `arb_sessions` للتدقيق.

## 5. الخيار البديل: MediaMTX (RTMP/WHIP عند تعذر P2P)

شبكات بعض اللاعبين تحجب P2P (UDP محجوب/NAT صارم) — عندها يحاول عميل اللاعب نشر شاشته عبر **WHIP** إلى MediaMTX يعمل على نفس الهاتف، والأدمن يشاهده عبر **WHEP** (وسم 🟠 عبر المرحّل).

**حالة هذا المضيف (2026-10-03): MediaMTX مُثبَّتٌ ومُشغَّل تحت pm2** —
`/root/mediamtx/mediamtx` إصدار **v1.21.1** (`linux_arm64`)، بصمته مطابقة لملف
`checksums.sha256`، وإعداده **`/root/DTSG/mediamtx.yml`** (إعداد المستودع لا نسخة
التوزيعة)، وتحته عملية pm2 باسم `mediamtx`. **وما زال ناقصاً:** `MEDIAMTX_WHIP_URL`
غير مضبوطة (احتياطي WHIP من v2.75 غير مفعّل) و`MEDIAMTX_RTMP_URL` غير مضبوطة
(⇒ **لا يمكن للاعب على هاتف نشر بثّه بعد** — §9)، فالمسار الحيّ يبقى **P2P حصراً**
في مسار الفيديو. أوامر التشغيل والتحقّق في §5.3، وإعداد الملف الكامل أدناه.

**التركيب (مرة واحدة) — إن أردتم تفعيل المرحّل:**
```bash
VER=v1.21.1                      # إصدار مثبَّت رقمياً — لا تستعملوا رابط latest
ARCH=linux_arm64                 # على x86_64: linux_amd64
mkdir -p /root/mediamtx && cd /root/mediamtx
wget -q "https://github.com/bluenviron/mediamtx/releases/download/${VER}/mediamtx_${VER}_${ARCH}.tar.gz"
wget -q "https://github.com/bluenviron/mediamtx/releases/download/${VER}/checksums.sha256"
tar -xzf "mediamtx_${VER}_${ARCH}.tar.gz"
sha256sum -c --ignore-missing checksums.sha256
cp /root/DTSG/mediamtx.yml ./mediamtx.yml # الإعداد المرفق بالمستودع (مُصحَّح في v2.81)
./mediamtx --version                # تحقّق: v1.21.1
```

> **[v2.81·تصحيح أمرين كانا لا يُنفَّذان]** رابط
> `releases/latest/download/mediamtx_linux_arm64v8.tar.gz` **يعيد 404 اليوم**:
> التسمية تغيّرت فصارت `mediamtx_<الإصدار>_linux_arm64.tar.gz` (بلا `v8`
> وبإصدار داخل الاسم). وثانياً `~/mediamtx` غير موجود على هذا المضيف أصلاً، فالأمر
> كان يفشل عند أول سطر.
>
> **ولا تشغّلوا `./mediamtx` في المقدمة ولا بـ`nohup … &`:** العملية بلا مشرف
> لا تعود بعد إعادة تشغيل الجهاز. المشرف المتاح فعلاً هو **pm2**
> (`pm2 start /root/mediamtx/mediamtx --name mediamtx --cwd /root/mediamtx -- /root/DTSG/mediamtx.yml && pm2 save`) — **وليس
> systemd**، إذ لا يدير المضيف العمليات بـsystemd أصلاً. التفاصيل في
> `docs/PHONE_HANDOFF_v281.md` §2.3، والنسخة المُنفَّذة على هذا المضيف في §5.3.

**تفعيل النظام (متغيرات بيئة الخادم — `.env.local` ثم `bash scripts/phone-env-restart.sh`):**
```bash
# [v2.81.1] سرّ اشتقاق رمز المسار — مطلوب، ويبقى في .env.local وحده (لا المستودع):
ARB_STREAM_SECRET=<سلسلة-عشوائية-طويلة>          # hex/base64 عشوائي ⇒ openssl rand -hex 32
MEDIAMTX_WHIP_URL=http://127.0.0.1:8889           # عنوان WHIP (نفسه يخدم WHEP)
ARB_STUN_URLS=stun:stun.l.google.com:19302,stun:stun1.l.google.com:19302
# [v2.81] المراقبة ومشاركة شاشة الهاتف (راجع §8 و§9):
MEDIAMTX_API_URL=http://127.0.0.1:9997    # افتراضي — لا يلزم كتابته إن لم يتغيّر
MEDIAMTX_RTMP_URL=rtmp://<عنوان-النفق-العام>:1935   # نشر شاشة الهاتف من الخارج
```

> **[v2.81.1] بند `ARB_STREAM_SECRET` — سرّ حقيقي، وميثاق تدويره:**
> يُشتق منه رمز المسار بـ`HMAC-SHA256` (انظر §5.2)، ويأخذ pathname بنيته من
> `server-mediamtx.js` وحده. **قواعده:** (1) في `.env.local` وحده — **لا في
> المستودع ولا في `mediamtx.yml`** (كلاهما معلن على GitHub)؛ (2) **لا يسجَّل في أي
> سجل ولا في `arb_stream_events` ولا في رسالة خطأ** — لا يُطبع إلا اسم المتغيّر؛ (3)
> **غيابه لا يُسقط المنصة** (يُولَّد سرّ عشوائي لهذا التشغيل مع تحذير إقلاع صريح،
> و`secretConfigured` = false) **لكنه يُبطل كل مسارات النشر عند كل إعادة تشغيل**؛
> (4) **تدويره يُبطل كل مسارات النشر الحيّة فوراً** ⇒ صيانة مقصودة فقط، والاعبين
> الذين نسخوا عناوينهم قبل التدوير يُقرأون «غير متصل» حتى يعيدوا النسخ.

> **[v2.81·تصحيح ادّعاء] `MEDIAMTX_WHIP_URL` ليس «موجوداً منذ v2.78» على هذا
> المضيف.** سطر الدليل القديم كان يعرضه ضمن «القائمة (كانت موجودة من v2.78 —
> لا تغيير)»، والفحص على `.env.local` حينها (2026-10-03) أعطى **صفر متغيّر يبدأ بـ
> `MEDIAMTX`** و**صفر يبدأ بـ`ARB_STUN`**. **(v2.81.1) ودخلت المتغيّراتُ منذ:**
> `ARB_STREAM_SECRET` و`MEDIAMTX_API_URL` (باستثناء `MEDIAMTX_WHIP_URL` و
> `MEDIAMTX_RTMP_URL` — الاثنان **ما زالا متعمَّداً غير مضبوطين** بانتظار قرار
> المالك عن وسيلة النقل العامة، §9.)**
> ⇒ **احتياطي WHIP (v2.75) لم يتفعّل على هذا الجهاز بعد.** **وهذا سليم:** النظام
> يعمل الآن بوضع **P2P حصراً** في مسار الفيديو (WebRTC مباشر بين اللاعبين)، فهو
> المسار الأساسي وهو ما تعمل عليه اللوحة فعلياً؛ والمرحّل المنشور تحت pm2 يخدم
> المراقبة (§8) لا مسار الفيديو. ولتفعيل WHIP ⇒ `MEDIAMTX_WHIP_URL=http://127.0.0.1:8889`
> ثم `phone-env-restart.sh`.

بدون `MEDIAMTX_WHIP_URL` يعمل النظام بوضع P2P حصراً (المحاولتان ثم فشل نظيف — لا مرحّل) — **وهذه هي الحالة الفعلية لهذا المضيف اليوم.**

**الدقة والخفة:** لا ترميز في MediaMTX (ترحيل فقط) — العميل يلتقط أصلاً بقيود خفيفة في `getDisplayMedia` (15–24 إطاراً و1280×720 كحد أقصى في arb-client.js — عدّلها لـ854×480 لمزيد من الخفة). إن أردت ترميزاً قسرياً 480p/720p أضفه في `mediamtx.yml` (وفّر المعالج — لا يُنصح به على هذا الهاتف).

### 5.1 المسارات — كتلة `~^dtsg` [v2.81] والمُرمَّزة [v2.81.1]

**[v2.81] المفتاح في `mediamtx.yml` تعبير نمطي `~^dtsg:` لا اسم حرفي `dtsg/`**،
لأنه يجب أن يغطي صيغتي النشر معاً — وإلا صار أحدهما خارج التغطية:

| الصيغة [v2.81] | من ينشرها | مفتاح `~^dtsg` يغطّيها |
|---|---|---|
| `dtsg/<roomId>/<playerId>` | تطبيق RTMP على الهاتف عند مشاركة الشاشة (§9) | ✅ |
| `dtsg-<roomId>-<userId>` | **الاحتياطي WHIP** — وهو ما ينشره `js/core/arb-client.js` فعلياً: السطر 227 يبني `roomId` + `-` + معرّف اللاعب (و`p` إن لم يكن محمّلاً)، ثم السطر 239 ينشره على `/whip/dtsg-` + ذلك | ✅ |

**[v2.81.1] والصيغتان المعتمدتان الآن مُرمَّزتان — اللاحقة `_` والرمز جزءٌ من
المسار لا تعليق، ولا يجوز نشر أيٍّ منهما بلا رمز:**

| الصيغة المعتمدة [v2.81.1] | من ينشرها |
|---|---|
| `dtsg/<roomId>/<userId>_<token>` | تطبيق RTMP على الهاتف عند مشاركة الشاشة (§9) |
| `dtsg-<roomId>-<userId>_<token>` | احتياطي WHIP (`arb-client.js`) |
| ~~`dtsg/<roomId>/<userId>`~~ | **مُهمَل عمداً** — لا يُقبل دليلاً على أي بثّ (§5.2) |

`token` = أول 16 خانة hex من `HMAC-SHA256(ARB_STREAM_SECRET, "<roomId>:<userId>")`،
ويولّده `server-mediamtx.js` (`publishPath()` / `publishPathWhip()`) لا الواجهة ولا
تطبيق الهاتف. **أين يذهب:** `relay.publish_path` و`relay.publish_path_whip` داخل
`/api/matches/mine` (المجالس غير المتفرّج في غرفته) و`mediamtx_publish_path` /
`mediamtx_publish_path_whip` داخل `POST /api/matches/:roomId/start-stream` (لاعب
نشط في غرفة `playing`) — أي **للاعب نفسه حصراً**، ولا تُكتب المسارات في أي جدول
ولا تُطبع في السجل.

**لماذا تغيّر الاسم [v2.81]؟** إعداد لم يكن MediaMTX v1.x يستطيع إقلاعه أصلاً،
ولم يُكتشف لأن الثنائي لم يكن مثبَّتاً على الهاتف يومها:
1. `dtsg/` — و`IsValidPathName` (internal/conf/path.go) ترفض أي اسم مسار ينتهي
   بشرطة مائلة ⇒ **الخادم يمتنع عن الإقلاع**.
2. `fallback: present` — وحقل `fallback` في v1.x حقل **إعادة توجيه** (redirect)
   لا يقبل إلا مساراً أو عنوان RTSP صالحاً ⇒ السلسلة `present` تُفشل التحقق.
   والمقصود أصلاً «يقبل هذا المسار من ينشر إليه» هو `source: publisher` وحدها،
   فحُذف السطر.

> ولا يُنهَ المفتاح أبداً بشرطة مائلة (`~^dtsg/`) — الشرطة الذيلة تُخرجه من
> دائرة التعابيرية فيعود رفض `IsValidPathName` نفسُه. (وهذا العيب — لا غياب الرمز —
> هو ما جعل الإعداد قالفالإقلاع، ولولا تركيب المرحّل تحت pm2 ما لكُشف ولا
> لوقع.)

### 5.1.1 حصر المستمعين على Loopback [v2.81.1]

افتراض MediaMTX هو **الربط على كل الواجهات**، فكان أي جهاز على شبكة الهاتف
(Wi-Fi) يصل مباشرةً إلى `1935/8554/8888/8889`. و[v2.81.1] كل مستمع مربوط بـ`127.0.0.1`:

```yaml
rtmpAddress: 127.0.0.1:1935     # الاستثناء الموثّق الوحيد — انظر أدناه
rtspAddress: 127.0.0.1:8554
hlsAddress:  127.0.0.1:8888
webrtcAddress: 127.0.0.1:8889   # WHIP/WHEP محليّان فقط
apiAddress:  127.0.0.1:9997     # من v2.81 — واجهة الاستعلام
```

⇒ **لا شيء يخرج عن الجهاز إلا عبر نفق يختاره المالك صراحةً.** وواجهة المراقبة
(9997) **غير قابلة للوصول علنياً**: قُدِّمت عند التثبيت بفحص عبر Cloudflare API —
النفق القائم `dmgames-local` له قاعدة ingress واحدة حصراً (catch-all إلى
`http://localhost:3000`) و**لا قاعدة توجّه 9997 ولا 8889 ولا 1935**.

> **⚠ الاستثناء الوحيد — خرقٌ مقصود إن اخترتم خيار الراوتر:** نشر 1935 عبر
> «توجيه منفذ من الراوتر» (§9) يفرض تحرير `rtmpAddress` إلى `:1935` بلا `127.0.0.1`
> ⇒ 1935 مكشوف على شبكة الهاتف وعبر الـIP العام. **ومع أن رمز المسار هو مصادقة
> النشر الوحيدة، فذاك أضعف الخيارات الثلاثة أمنياً** — النفق (playit/VPS) أفضل
> لأنه يبقى المنفذ محشوراً على Loopback والوصول كله عبر قناة واحدة يمكن إيقافها.

### 5.2 ✅ بند مصادقة النشر على `~^dtsg` — **مُغلق [v2.81.1]** ببرمز داخل المسار

> **كان بنداً مفتوحاً في v2.81، وكُتب حينها بعبارة «يحتاج قرار المالك». لم يعد
> ينتظر قراراً: الأثر امسّ قراراً يُفرج عن المال، فأُغلق بالآلية.**

**الخطر كما وُثّق في v2.81 (ويبقى صحيحاً كوصف للوضع قبل الإصلاح):** كتلة المسارات
`~^dtsg` **بلا أي مصادقة نشر** — `publishUser` و`publishPass` مهجوران في v1.x —
فكل من يصل إلى منفذ RTMP 1935 يستطيع النشر في مسار أي غرفة، **ولا يصحّ الاعتماد
على ظاهر المسار بوصفه مفتاحاً سرّياً**: `roomId` و`userId` أرقام صغيرة و`roomId`
هو نفسه رمز غرفة التحكيم المفتوحة في لوحة الأدمن ⇒ التخمين عمليّ. والأثر أن
`GET /api/matches/:roomId/stream-status` (§8.1) كانت تستنتج «هذا اللاعب بعينه يبث»
من مجرّد جاهزية المسار ⇒ **انتحال بثّ الخصم أمام الأدمن في قرار حسم يُفرج عن
الإيداعات**.

**ما نُفِّذ:** الخيار (أ) من المرشَّحين — لا بلغة «توكن جلسة عشوائي» بل باشتقاق
حتمي مشتقّ من سرّ الخادم:

| | |
|---|---|
| **المفتاح** | `HMAC-SHA256(ARB_STREAM_SECRET, "<roomId>:<userId>")` مقصوصاً على أول 16 خانة hex |
| **الصيغ** | `dtsg/<roomId>/<userId>_<token>` (RTMP) · `dtsg-<roomId>-<userId>_<token>` (WHIP) |
| **السرّ** | `ARB_STREAM_SECRET` في `.env.local` وحده (قواعده في §5) |
| **التوزيع** | اللاعب الجالس النشط في غرفته فقط، عبر `mine()` و`startStream()` |
| **التحقق** | المراقب **لا يثق بالمسار المجرّد**: `pathVariants()` يعيد الصيغتين المُرمَّزتين حصراً ويُعيد اشتقاقهما من السرّ نفسه ⇒ «جاهز» بلا رمز صحيح = لا دليل على شيء |
| **الثبات** | نفس (غرفة × لاعب) ⇒ نفس الرمز ⇒ لا تخزين ولا مزامنة، ويعمل بعد إعادة التشغيل ما دام السرّ ثابتاً |

**ودليل إغلاقه مادّياً (لا نظري):** نشر `ffmpeg` RTMP حقيقي على المرحّل المشغَّل —
النشر على المسار **المجرّد** `dtsg/r7/1` **لم** يُبلَّغ أنه اللاعب متصل، والنشر
على المسار **المُرمَّز** **أُبلِغ `online`** ببايتات غير صفرية ومدة بث صحيحة.

**ما لم يُنفَّذ (الخيار ب) ولماذا:** `authInternalUsers` بسرّ مشترك داخل MediaMTX.
**MediaMTX نفسه يبقى بلا مصادقة نشر** — الرمز هو **طبقة المصادقة الوحيدة**، وهذا
مقبول تحديداً لأن الجاهزية لم تعد دليلاً على هوية اللاعب بلا رمز صحيح؛ فإضافة
طبقة ثانية تعني سرّاً إضافياً في إعداد خارج المستودع بلا فائدة تُذكر هنا. ولا
تُفتح بوابة «النشر بلا مصادقة» في أي مراجعة أمنية لاحقة.

**ما بقي بالحرف من بند v2.81 (الإجراءات الاحترازية):** لا تُخرجوا 1935 للعالم إلا
عند الحاجة، وأوقفوا النفق فور انتهاء الاختبار الميداني. ونفس البند في
`docs/PHONE_HANDOFF_v281.md` §4 بند 3.

**تنبيه شبكة:** واجهة المراقبة 9997 **محشورة داخل الجهاز** ولا تُوجَّه عبر النفق
أبداً (قيد «صفر باندويث»؛ وفُحصت عددياً في v2.81.1 — §5.1.1). وMediaMTX يستمع
محلياً ⇒ وصول الأدمن إليه من الخارج يتطلب النفق المختار للـ1935 أو شبكة الهاتف
أو VPN. أبقِ P2P هو المسار الأساسي؛ المرحّل احتياطي.

### 5.3 التشغيل تحت pm2 — ما نُفِّذ فعلاً على هذا المضيف [v2.81.1]

المرحّل **مُثبَّتٌ ويشتغل تحت pm2 الآن** (لا خطوة قادمة). الأوامر كما نُفِّذت،
بما فيها **تمرير الإعداد كوسيط صريح** — وهو الشرط الذي أضاع أول محاولة:

```bash
# (بعد نسخ /root/DTSG/mediamtx.yml إلى مجلد العمل — انظر §5 أعلاه)
pm2 start /root/mediamtx/mediamtx --name mediamtx --cwd /root/mediamtx -- /root/DTSG/mediamtx.yml
pm2 save                       # ليعود بعد إعادة تشغيل الجهاز

# التحقّق — والأهمّ السطر الثاني:
pm2 status | grep mediamtx                       # ⇒ online
pm2 describe mediamtx | grep 'script args'       # ⇒ /root/DTSG/mediamtx.yml   ← لا فارغ
curl -s http://127.0.0.1:9997/v3/paths/list      # ⇒ JSON ⇒ الواجهة حيّة
```

**⚠ ولماذا يُكتب هذا التحقّق بلا لبس:** **أول تشغيل** تحت pm2 **لم يكن الإعداد
مُمرَّراً** ⇒ بحث MediaMTX عن `mediamtx.yml` بجوار الثنائي فلم يجده، فاستقال على
**إعداداته الافتراضية بصمت بلا خطأ واحد** — وكل المنافذ على **كل الواجهات**
(1935/8554/8888/8889/9997 مكشوفة على شبكة الهاتف) و**بلا كتلة `~^dtsg` أصلاً**
(لا قيود مسارات إطلاقاً)، وpm2 كان يُظهر `online` بلا تذييل.
⇒ **القاعدة المستفادة: `online` دليل تشغيل لا دليل إعداد — تحقّق من `script args`
قبل أن تثق بأي إعداد.** ولهذا السطر في قائمة التحقّق أعلاه غير اختياري.

### 7.1 متطلبات مشاركة الشاشة [v2.78] — رسائل دقيقة بلا تضليل

بلاغ المالك الموثق: «رسالة تقول إن المتصفح لا يدعم مشاركة الشاشة مع أنه كروم» —
الجذر ليس عطلاً في الكود بل غياب تمييز الأسباب؛ كروم **يحجب** واجهة البث في
حالتين شائعتين، و`arb-client.js` صار يفصل بينهما برسالة صحيحة لكل حالة:

| التشخيص (`ARB.support()`) | الشرط الفعلي | الرسالة |
|---|---|---|
| `insecure` | فتح المنصة عبر `http://` غير المحلي — كروم يحجب `navigator.mediaDevices` كلياً | «تتطلب اتصالاً مشفراً HTTPS — افتح المنصة عبر رابطها الرسمي» |
| `mobile` | متصفح هاتف (كروم أندرويد / WebView / متصفحات التطبيقات): `mediaDevices` موجودة و`getDisplayMedia` غائبة — **قيد منصّي في كل متصفحات الجوال، لا عطب** | «متصفح الهاتف لا يدعم مشاركة الشاشة — افتح المنصة من حاسوب (كروم/إيدج/فايرفوكس)» |
| `old` | متصفح مكتبي قديم (كروم < 72) | «حدّث متصفحك إلى أحدث إصدار» |
| `ok` | الواجهة متاحة | زر البث الذهبي المعتاد |

- الزر نفسه يتحول إلى وضع تحذيري (⚠️ غير متاحة هنا) مع الشرح داخل الصندوق —
  داخل مودال الغرفة وصفحة `#arb` معاً، فلا يفاجأ اللاعب بعد النقر.
- أخطاء الالتقاط صارت مصنفة كذلك: `NotAllowedError` (رفض الإذن)،
  `NotReadableError`/`AbortError` (الشاشة مشغولة ببرنامج تصوير آخر)،
  و`OverconstrainedError` (إعادة محاولة تلقائية بقيود مجردة).
- **الخلاصة التشغيلية للاعبين:** البث من **حاسوب** بمتصفح حديث عبر **HTTPS**
  حصراً؛ مراقبة الأدمن تعمل من أي جهاز (لا تلزمها واجهة الالتقاط).

**الاختبارات:** `QA_BASE=http://127.0.0.1:3971/ node tests/_v275_arbitration_test.js` — 30/30 فحصاً (REST + حراسة + إشارات + حسم/نزاع + بث P2P حقيقي حتى ظهور الفيديو عند الأدمن). ملاحظة بيئة: `getDisplayMedia` في المتصفحات بلا واجهة يفشل — الجنحة تستبدله بمجرى Canvas تركيبي لنفس مسار WebRTC الحقيقي.

```json
}
```

- **منطق المسارات [v2.81.1]:** يُفحص **النمطان المُرمَّزان** معاً —
  `dtsg/<roomId>/<userId>_<token>` (مسار RTMP لنشر شاشة الهاتف §9) و
  `dtsg-<roomId>-<userId>_<token>` (مسار WHIP الصادر من `arb-client.js`) — أول
  مسار جاهز هو الحكم. **وكلاهما مشتقّ من `ARB_STREAM_SECRET`** فيعيد المراقب
  اشتقاقهما للمقارنة، **والمسار المجرّد بلا رمز لا يُستعلَم عنه ولا يُصدَّق**
  (`pathVariants()` يعيد الصيغتين المُرمَّزتين حصراً — §5.2). كتلة المسارات التي
  يستجيب لها المرحّل هي `~^dtsg` (انظر §5.1).
- **الحراسة:** 401 بلا جلسة · 403 لغير الأدمن · 404 غرفة مجهولة.
- **[v2.81·انزياح حقول API — مُصلَح]:** الوحدة كانت تقرأ `ready` و
  `bytesReceived` وحقل `readyDuration`. الحقلان الأولان **ما زالا يُبَثّان
  لكنهما مهجوران**، و`readyDuration` **حُذف** من الإصدارات الحديثة وحلّت
  محلّه تواريخ RFC3339. والنتيجة: حالة البث كانت تُقرأ `false` على أي مرحّل
  حديث رغم أن البث قائم. الآن تُقبل الصيغتان معاً:
  `online`/`inboundBytes` المعتمدان اليوم، و`readyTime`/`onlineTime` للمدة.
- **[v2.81·إصلاح تعليق — مُصلَح]:** طلب HTTP إلى المرحّل كان **لا يستدعي
  نداءه الراجع إطلاقاً** إذا قطع المرحّل المقبس في منتصف الجسم (لا `end` ولا
  `error`) ⇒ طلب الأدمن يعلق إلى الأبد، ومع `maxSockets:4` المشترك يتجمّد
  الاستعلام **لكل الغرف** على المنصة كلها لا لغرفة واحدة. الآن النداء الراجع
  ينحسم **مرة واحدة على كل طريق** (`error` · `aborted` · `timeout` · حارس زمني
  مُصفَّر عند الحسم) — **بلا حلقة خلفية** ⇒ القيد 2 أعلاه يبقى قائماً.
- **[v2.81·لا مال · مُتحقَّق منه ساكناً]:** لا `UPDATE`/`INSERT`/`DELETE` على
  `users`/`transactions`/`rounds`/`bet_tickets`/`refunds` في الوحدة إطلاقاً —
  والمكتوب الوحيد هو `arb_stream_events` (سجل تدقيق، بلا رصيد).

### 8.2 تنبيه الانقطاع (>30ث) — «دون تعديل الرصيد تلقائياً»

بالذاكرة لكل (غرفة×لاعب)، والاستعلام على الطلب يعني أن لوحة مفتوحة (استطلاع
10ث) تكشف الانقطاع فور تجاوز مهلة المراقبة، ولوحة مغلقة لا تستهلك شيئاً:

1. **انقطاع لمن سبق له البث** أثناء جلسة حية ⇒ يُثبَّت `offlineSince`؛ تجاوز
   `MEDIAMTX_WATCH_TIMEOUT_MS` (افتراضه 30ث) ⇒ **تنبيه واحد لكل نوبة**:
   صف في SQLite (`arb_stream_events` — للتدقيق حصراً) + حدث SSE **`arb:stream`**
   للأدمن/السوبر حصراً + toast 🚨 في لوحة التحكيم.
2. **العودة** ⇒ حدث `recovered` بصفه وtoast 🟠.
3. **من لم ينشر قط لا يُنذر** (الانقطاع لمن سبق له البث حصراً — لا إنذار كاذب
   لمن لم يبدأ).
4. **لا يُمسّ أي رصيد مهما حصل** — القرار النهائي للأدمن حصراً (نص المستند حرفياً).

### 8.3 تفعيل المراقبة — **مُفعَّل فعلاً [v2.81.1]**

> **ما نُفِّذ:** المرحّل **مثبَّت تحت pm2** على هذا المضيف (§5 و§5.3)، و
> `api: yes` + `apiAddress: 127.0.0.1:9997` في `mediamtx.yml` **قيد التشغيل
> الآن**، و`MEDIAMTX_API_URL` مضبوط ⇒ **نقطة `stream-status` تقرأ مرحّلاً حقيقياً،
> لا صفراً**، وأول سطر في لوحة الأدمن السيّئ قابل للقراءة. (وإن توقّف المرحّل
> فالنتيجة المتوقَّعة **ليست** غياب السطر بل شريحة **«⚫ المرحّل لا يرد»** §8.4.)

```yaml
# mediamtx.yml — تفعيل واجهة الاستعلام الداخلية (محشورة داخل الجهاز حصراً):
api: yes
apiAddress: 127.0.0.1:9997
```
```bash
# .env.local ثم bash scripts/phone-env-restart.sh (لا يلزم إن كان الافتراضي):
MEDIAMTX_API_URL=http://127.0.0.1:9997
ARB_STREAM_SECRET=<سلسلة-عشوائية-طويلة>   # [v2.81.1] مطلوب — رمز المسار (§5.2)
# التحقق بعد إعادة تشغيل MediaMTX:
pm2 restart mediamtx && pm2 save
curl -s http://127.0.0.1:9997/v3/paths/list
```

### 8.4 ما يظهر عند الأدمن

سطر حالة تحت فيديو كل لاعب في المشاهدة المزدوجة (استطلاع 10ث + أحداث SSE):
`🟠 المرحّل مباشر · 3.0MB · 1:35` عند البث، و`🚨 انقطع عبر المرحّل (2د)` بعد
تجاوز المهلة — والشريحة تُحدَّث في مكانها بلا مسّ للفيديوهات (نمط بوابة
التوقّع v2.77 — لا وميض).

**[v2.81] حالة رابعة — «المرحّل لا يرد»:** كان `available:false` (المرحّل
ميت أو غير مركّب) يُخزَّن ولا يُعرض، فصار **«المرحّل مطفي» و«اللاعب سكت» شيئاً
واحداً** في عين الأدمن — وهي بالضبط الحالة التي قد يبنى عليها قرار حسم. الآن
تُرسم شريحة صريحة **`⚫ المرحّل لا يرد`** (مفتاح i18n جديد `arb.relayDown`
مترجم ×4) متى رجع `available:false`، وتعود لحالتها السابقة تلقائياً أول ما
يستجيب الاستطلاع. لا تمسّ الفيديو ولا تُعيد رسم المشاهدة.

## 9. مشاركة شاشة الهاتف — البديل التقني [v2.81]

**الجذر:** متصفحات الجوال كلها (أندرويد/iOS) لا توفّر `getDisplayMedia` —
قيد منصّي لا حلّ برمجياً داخل المتصفح (توثيق v2.78 §7.1). **البديل المعتمد
بتوجيه المالك:** اللاعب يبث شاشة هاتفه بتطبيق بث RTMP مجاني (مثل **Larix
Screencer**) إلى MediaMTX على خادم المنصة، والأدمن يشاهده عبر المرحّل نفسه —
دون أي حاسوب وضمن المنظومة القائمة دون تعديل معماري.
**[v2.81·تصحيح]:** عبارة «الموجود أصلاً» الواردة في صيغة سابقة من هذا القسم
كانت خاطئة — المرحّل **غير مثبَّت** على خادم الهاتف يومها؛ **(v2.81.1) وصار اليوم
مثبَّتاً تحت pm2** (§5 · §5.3) ⇒ فالأدق الآن: إلى MediaMTX على خادم المنصة.

**تدفق البث من الهاتف ([v2.81.1] بالمسار المُرمَّز):**
```
تطبيق RTMP على الهاتف (Larix Screencer)
   → rtmp://<عنوان-عام>:1935/dtsg/<roomId>/<userId>_<token>   (MEDIAMTX_RTMP_URL + المسار من start-stream)
   → MediaMTX على خادم الهاتف (استقبال RTMP — ترحيل بلا ترميز)
   → الأدمن يشاهد عبر WHEP/WebRTC في لوحة التحكيم (المشاهدة المزدوجة المعتادة)
```
مسار النشر يحمل **معرّف غرفة اللاعب ومعرّفه** (عنوان عام عمداً، **ليس سرّاً**) و
**لاحقةَ رمز مشتقّة من `ARB_STREAM_SECRET`** — وهي **الجزء السرّي**، وتعرضها المنصة
للاعب نفسه في صفحة **التحكيم المباشر** (`#arb`) ببطاقة إرشادية «📱 مشاركة شاشة
الهاتف» تظهر **للاعب على هاتف حصراً** (reason === 'mobile') مع زر 📋 نسخ — ومشاركة
المتصفح من حاسوب تبقى كما كانت بلا مساس (المكتسبات).

> **[v2.81.1] التصحيح الأمانوي المهم — المسار لم يعد بياناً عادياً:** الصيغة
> `dtsg/<roomId>/<userId>` المكشوفة التخمين (معرّفات صغيرة + رمز الغرفة ظاهر في
> لوحة الأدمن) **تسمح بالانتحال**، ولا مصادقة نشر على كتلة `~^dtsg`. وقد كانت
> هذه **بنداً مفتوحاً يطلب قرار المالك في §5.2** — **أُغلق v2.81.1 ببرمز داخل
> المسار** مشتقّ من سرّ الخادم، والمسار المُرمَّز هو **مفتاح لا يُخمَّن**؛ فأصبح
> العنوان العام وحده هو المتغيّر الحرّ، وهو ليس سرّاً. (**ما زال ينقص المتغيّر
> الحرّ فعلاً:** `MEDIAMTX_RTMP_URL` غير مضبوط ⇒ لا يُنشر شيء من الهاتف بعد —
> انظر نهاية هذا القسم.)

**ما نفّذته المنصة (جهة الويب):**
- `server-arbitration.js`: بيانات المرحّل في `/api/matches/mine` (`relay.rtmp`) والتوكن (`mediamtx_rtmp`) — **بلا أسرار: العنوان عام** يبنيه المالك في `.env.local`؛ **و[v2.81.1] أضيفت المسارات المُرمَّزة** `relay.publish_path`/`_publish_path_whip` و`mediamtx_publish_path`/`_publish_path_whip` **لِلاعب الجالس النشط في غرفته حصراً**.
- `arb-page.js`: البطاقة الإرشادية (خطوات ×4 لغات + نسخ العنوان) + الزر يبقى وضعاً تحذيرياً ⚠️ على الهاتف ولا تُمحوه شريحة الحالة.
- `arb-client.js`: سطر تلميح «البديل على الهاتف» داخل مودال الغرفة.
- `arb-admin.js` + `server-mediamtx.js`: سطر حالة المرحّل وتنبيه الانقطاع/العودة (§8).
- i18n: مفاتيح `arb.mr*` التسعة مترجمة ×4 (عربية/فرنسية/إنجليزية/دارجة).

**ما يلزم على خادم الهاتف (جهة المسؤول ومساعديه) — ما تبقّى منها فقط [v2.81.1]:**
- ✅ **مُنجَز:** تثبيت MediaMTX وتشغيله تحت pm2 (§5 · §5.3) · تحديث `mediamtx.yml` وإعادة التشغيل · ضبط `ARB_STREAM_SECRET` و`MEDIAMTX_API_URL` في `.env.local`.
- ⛔ **متبقٍّ:** **توجيه منفذ RTMP 1935 عبر نفق عام** ثم ضبط `MEDIAMTX_RTMP_URL` — **وهذا قرار المالك وحده**، والخيارات الثلاثة مرتّبة بالأفضلية: `playit.gg` نفق TCP · `socat` على VPS · توجيه منفذ من الراوتر **وهو الأضعف**؛ والاختيار الكامل وتحذيراته في **`docs/PHONE_HANDOFF_v281.md` §4**.

> ⚠️ **ما لا يُكتب في أي مكان: أن الميزة مكتملة.** `MEDIAMTX_RTMP_URL` **غير
> مضبوط** ⇒ **جهة المراقبة حيّة ومُفعَّلة فعلاً** (المرحّل تحت pm2 + `stream-status`
> يقرأ مرحّلاً حقيقياً + المسارات مُرمَّزة)، **أمّا نشرُ شاشة الهاتف من خارج
> الجهاز فغير ممكن بعد** — لا عنوان عام ⇒ لا لاعب على هاتف يستطيع البدء بالنشر.
> الميزة نصفُ جاهزة: لا ميتة، ولا يُجوز أن تُوصف بأنها مكتملة.
